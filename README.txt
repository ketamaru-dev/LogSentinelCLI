Техническое задание (ТЗ): Разработка консольной утилиты «LogSentinel CLI»
Статус: К реализации
Исполнитель: Junior Python Developer
1. Общее описание проекта
LogSentinel CLI — это асинхронная консольная утилита для сканирования, парсинга и аудита файлов логов.
Программа должна принимать путь к директории с логами, параллельно обрабатывать файлы построчно,
выявлять аномалии и ошибки с помощью гибкой иерархии парсеров, а затем формировать сводный отчет в формате JSON.
Утилита должна демонстрировать чистоту архитектуры, использование ООП, безопасную обработку исключений и
эффективную работу с памятью (асинхронные генераторы).
2. Архитектурные требования и стек
* Язык: Python 3.12+
* Асинхронность: asyncio (async/await, asyncio.gather, асинхронные генераторы с yield)
* Работа с файлами и путями: pathlib.Path
* Сериализация данных: json
* Интерфейс командной среды: аргументы через sys.argv
* ООП: Абстрактные базовые классы (abc), наследование, полиморфизм, инкапсуляция, свойства (@property)
* Декораторы и контекстные менеджеры: кастомные декораторы для логирования/замера времени и контекстные
менеджеры (contextlib или через классы)
3. Структура проекта
Репозиторий проекта должен быть организован следующим образом:
Plaintext

log_sentinel/
├── venv/                      # Виртуальное окружение
├── logs/                      # Директория с тестовыми логами (.log файлы)
├── reports/                   # Директория для сохранения JSON-отчетов
├── exceptions.py              # Иерархия кастомных исключений
├── parsers.py                 # ООП-архитектура парсеров (ABC и реализации)
├── utils.py                   # Декораторы и контекстные менеджеры
├── main.py                    # Точка входа, оркестрация через asyncio
└── requirements.txt           # Зависимости проекта
4. Детализированные задачи по модулям
Задача 1: Иерархия исключений (exceptions.py)
Создать собственные классы ошибок, наследуемые от базового Exception:
* LogSentinelError — главный базовый класс для всех ошибок утилиты.
* FileReadError — вызывается при проблемах с чтением файла (файл не найден, нет прав). Должен содержать
атрибут пути к файлу.
* LogFormatError — вызывается при критической ошибке разбора строки.
Задача 2: ООП-архитектура парсеров (parsers.py)
Разработать иерархию классов для анализа логов:
1. Абстрактный класс BaseParser (используя abc.ABC и @abstractmethod):
    * Должен содержать защищенные или приватные атрибуты состояния (например, счетчик обработанных строк и
    найденных ошибок).
    * Обязательный абстрактный метод parse_line(self, line: str) -> dict.
    * Свойства (@property) для получения текущей статистики парсера.
2. Конкретные парсеры (минимум два):
    * StandardLogParser — разбирает стандартные строковые логи (ожидает дату, уровень вроде INFO/ERROR и текст).
    * GenericFallbackParser — универсальный парсер, который ищет ошибки по ключевым словам (ERROR, CRITICAL,
    Exception, Failed) для файлов с неизвестной структурой.
Задача 3: Инфраструктурные компоненты (utils.py)
Написать вспомогательные инструменты:
1. Декоратор (log_execution_time):
    * Универсальный декоратор (принимает аргументы включения логов), который замеряет время выполнения функций
    парсинга и логирует результат.
2. Контекстный менеджер (AuditSession):
    * Управляет жизненным циклом сессии: фиксирует время старта, выводит приветствие в консоль, а в блоке
    finally (даже при возникновении ошибок) сохраняет итоговый словарь отчета в файл reports/audit_report.json с
    помощью pathlib.
Задача 4: Асинхронный движок и CLI (main.py)
Реализовать точку входа и логику обработки:
1. Написать асинхронный генератор для построчного чтения файлов логов (async def read_file_lines(filepath)),
чтобы не перегружать оперативную память большими файлами.
2. С помощью sys считывать аргументы командной строки (например, путь к папке с логами).
3. Используя pathlib.Path, находить все .log файлы в целевой директории.
4. Организовать параллельный запуск обработки файлов через asyncio.gather.
5. Использовать коллекции (set для уникальных типов ошибок, dict для статистики) для агрегации данных.
5. Критерии приемки (Definition of Done)
* Код запускается без ошибок через терминал.
* Все компоненты покрыты аннотациями типов (typing).
* При передаче битого файла или отсутствующего файла утилита не падает с системным Traceback, а корректно
обрабатывает ошибку через кастомные исключения.
* Итоговый JSON-отчет успешно генерируется в папке reports/.
